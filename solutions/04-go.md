# Loesung 04 - Go ueber PKCS#11

## Lauf

```bash
make init-token
make gen-rsa
make go-demo
```

Erwartet:

```text
Token: dev-token
Signatur: /workspace/lab/work/go.sig (...)
Verified OK
```

## Kernablauf im Code

`lab/go/pkcs11-demo/main.go` macht:

1. `pkcs11.New(modulePath)` und `Initialize()`.
2. Slots mit Token ueber `GetSlotList(true)`.
3. `GetTokenInfo(slot)` und Label-Match gegen `dev-token`.
4. `OpenSession` und `Login(CKU_USER, pin)`.
5. Key-Suche mit:
   - `CKA_CLASS = CKO_PRIVATE_KEY`
   - `CKA_ID = []byte{0x01}`
6. Signatur mit `CKM_SHA256_RSA_PKCS`.
7. Public-Key-Export und OpenSSL-Verifikation ueber das Lab-Skript.

## Fehler pruefen

`make`-Targets ueber `gen-rsa`/`init-token` koennen mit veraenderter PIN/Label gar nicht erst durchlaufen. Daher die Vorstufe sauber rendern und nur die Go-Demo mit der Manipulation starten.

Falsche PIN:

```bash
make init-token gen-rsa
docker compose -f lab/docker-compose.yml run --rm \
  -e PKCS11_USER_PIN=000000 \
  pkcs11-go bash -lc 'lab/scripts/13-go-demo.sh'
```

Erwartet: `C_Login: CKR_PIN_INCORRECT`.

Token-Label, das es nicht gibt — Demo direkt aufrufen, damit `init-token` nicht einfach ein neues Token mit diesem Label anlegt:

```bash
make init-token gen-rsa
docker compose -f lab/docker-compose.yml run --rm \
  -e PKCS11_TOKEN_LABEL=missing \
  pkcs11-go bash -lc 'cd lab/go/pkcs11-demo && go run .'
```

Erwartet: klare Meldung, dass kein Slot mit diesem Token-Label gefunden wurde.

## Antworten zu den Reflexionsfragen

**1. (Recall) Objekt-Handle ist sessionspezifisch:** PKCS#11 §11.7 sagt explizit, dass `CK_OBJECT_HANDLE` nur innerhalb der Session gilt, in der es zurueckgegeben wurde. Token-persistente Objekte (`CKA_TOKEN=true`) ueberleben Session-Wechsel, ihre Handles aber nicht — dieselbe Anwendung mit einer neuen Session bekommt potenziell andere Zahlenwerte fuer dieselben Objekte. Der stabile Identifier ist `CKA_ID` (oder Label), nicht das Handle. Wer Handles persistiert (z.B. in einen Cache oder eine DB), riskiert `CKR_OBJECT_HANDLE_INVALID` nach Reconnect.

**2. (Analyse) Slot ueber Token-Label:** Slot-IDs sind nicht stabil — siehe Loesung 01. Die Go-Demo ruft `GetSlotList(tokenPresent=true)`, iteriert ueber alle Slots, ruft `GetTokenInfo(slot)` auf und matcht das Label gegen `dev-token`. Zwei reale Szenarien, die eine Slot-Index-Loesung brechen:

- **Lab-reproduzierbar:** `make clean-tokens && make init-token` — SoftHSM verschiebt das initialisierte Token typisch von Slot `0` auf einen anderen Slot (deterministische, aber nicht index-`0`-Wert). Wer `slotListIndex=0` hartcodiert hat (siehe `softhsm.cfg` der Java-Demo), greift dann ins Leere.
- **Produktiv:** zweites Token an demselben Modul. Smartcard-Reader mit zwei Karten, USB-HSM-Cluster mit drei Partitionen, oder ein Multi-Tenant-HSM. Die `GetSlotList`-Reihenfolge ist von Library und Vendor abhaengig und kann sich zwischen Builds aendern.

**3. (Analyse) pkcs11-spy einhaengen:** Der Demo-Code laedt das Modul ueber `pkcs11.New(modulePath)` mit dem Pfad aus `PKCS11_MODULE`. `pkcs11-spy.so` ist selbst eine PKCS#11-Library, die zwischengeschaltet wird. Aufrufpfad:

```bash
PKCS11SPY=/usr/lib/softhsm/libsofthsm2.so \
PKCS11SPY_OUTPUT=/tmp/spy.log \
PKCS11_MODULE=/usr/lib/x86_64-linux-gnu/pkcs11/pkcs11-spy.so \
  make go-demo
```

Kein Code-Change. Spy laedt SoftHSM, leitet alle Calls durch und logt sie. Genau das ist die Mechanik aus Kap. 08 §"OpenSC Spy".

**4. (Evaluate) Erste Schicht ueber miekg:** Die meisten produktiven Setups ziehen **zuerst** einen Session-Pool ein (Pattern aus Kap. 17). Begruendung: ohne Pool wird der "ein Service mit n Goroutinen, eine Session" zur Falle — `CKR_OPERATION_ACTIVE` ist unter Last sicher, weil PKCS#11-Sessions im Binding nicht thread-safe sind (siehe Kap. 17 Tabelle "Thread-Safety pro Binding").

Unsichtbare Kosten, wenn man *keinen* Pool baut: bei niedriger Last sieht alles in Ordnung aus; erst unter Lasttest oder im ersten produktiven Trafficpeak meldet sich `CKR_OPERATION_ACTIVE`, manchmal als nichtdeterministische Korruption (Sign-Resultat einer Anfrage in Response einer anderen). Dazu kommt: jede zweite Wahl (eigene Wrapper, Cleanup-Pattern) baut man auf einer korrekten Concurrency-Basis viel sauberer; ohne Pool kapselst du eine kaputte Architektur.

Reasonable Alternative: ein `crypto.Signer`-Adapter zuerst (wie in Kap. 14 §"Bridge-Problem 1"), wenn der Service vor allem mit Standard-Crypto-Libs (CMS, JWT, x509) interoperieren muss. Dann ist die Pool-Schicht der zweite Schritt. Aber: ohne Concurrency-Antwort bleibt der Service brittle.
